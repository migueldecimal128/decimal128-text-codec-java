# decimal128-text-codec-java

Thin codec between the two IEEE 754-2019 decimal128 interchange encodings — BID
and DPD — and decimal character sequences, for Java.

Ported from `decimal128-text-codec-kotlin`, which descends from
`decimal128-kotlin-legacy/decimal128-bid-string-codec`. One file, one class, no
runtime dependencies.

## API

```java
import com.decimal128.textcodec.Decimal128TextCodec;

// bits -> text
String s = Decimal128TextCodec.bid128ToString(hi, lo);
String d = Decimal128TextCodec.dpd128ToString(hi, lo);

// text -> bits; returns null on success, an error message on failure
long[] bits = new long[2];
String err = Decimal128TextCodec.bid128Parse(bits, "1.23E+45");
String errD = Decimal128TextCodec.dpd128Parse(bits, "1.23E+45");
```

Values are a pair of `long`s: index 0 is the high 64 bits of the encoding,
index 1 the low 64. Both parse functions always write `out` — the canonical
positive quiet NaN on failure — so a caller who ignores the return value still
observes a legal IEEE 754-2019 datum.

## Scope

Rounding, where required, is `roundTiesToEven` and is not configurable. Output
is the GDAS `to-scientific-string` form and is not configurable — the exponent
sign is always written (`6.02E+23`), and cohort information is preserved. No
arithmetic, no field extraction, no value-type wrapper.

Accepted input matches what the full `decimal128-{lang}` ports accept. That
includes the parenthesised NaN payload: **`NaN(123)` as well as `NaN123`**,
matching the spelling C's `strtod` reads. The form is positional and balanced —
`(` immediately after the word, at least one digit, `)` last — so `NaN()`,
`NaN(1`, `NaN(1)2(3)`, `NaN[1]` and `NaN{1}` are all rejected. Rendering never
emits parentheses. The codecs had this before the ports did; the ports took it
on 2026-08-23, closing the family's one grammar divergence.

For the full decimal128 implementation see `decimal128-java` at
<https://decimal128.com>.

## Requirements

Java 21. The only version-sensitive call is `Math.unsignedMultiplyHigh`, which
arrived in Java 18 and is where this port differs from its siblings: they carry
a hand-rolled 32×32 decomposition because their targets have no such primitive,
while HotSpot intrinsifies the JDK one to the machine's widening multiply. Every
call site is identical to theirs; only that one body is not.

Internal-consistency claims — the ones unreachable for any input — are spelled
as `assert`, which is this language's form of the compile-time `verify` flag the
sibling ports use, and shares the property that matters: the expression is not
evaluated when the checks are off. Gradle arms assertions on test tasks, and the
build states it rather than relying on the default, so the whole corpus runs
with every claim live. The one check that must survive into a shipping build —
the coefficient-width invariant standing in for the removed precision-truncation
step — is an unconditional throw instead.

## Tests

```
git submodule update --init --recursive
./gradlew test
```

Two test classes in one file. The canonical table is its own class but shares a
file with the other tables, so the two table runners they both use stay
package-private to it — the same layout the C, Swift and Kotlin ports use.

| file | what it covers |
|---|---|
| `src/test/java/.../TestCorpusVectors.java` | `TestCorpusVectors` — the four conformance tables over the shared corpus, 2,601 rows, both directions, both formats. Also holds the corpus reader, the loader and the hex helpers, its only consumer. |
| | `TestCanonicalCorpus` — the full 84,783-row canonical table |

That is the whole suite, and the shape is deliberate: **every test vector in this
repo comes from the shared corpus.** There is no hand-written table, and nothing
reaches past the four public methods.

The repo is standalone: it depends on no decimal128 port, at runtime or in
tests. The independent oracle is the shared `text_bid_dpd` corpus, generated by
the decimal128-c engine, which reaches its answers by different algorithms than
this codec does.

The vectors are read from `resources/text_bid_dpd`, where `resources` is the
`decimal128-resources` submodule — the same mount every decimal128 port uses.
Nothing is copied into this repo, so there is no drift class to police, and
nothing is copied onto the test classpath either: the loader reads the submodule
working tree directly. The build hands the test task the absolute corpus root in
`DECIMAL128_RESOURCES`, so the runner's working directory does not matter. The
Kotlin port needs a KMP `expect`/`actual` seam to reach a data file at all; here
the loader is three lines and lives with its only caller.
